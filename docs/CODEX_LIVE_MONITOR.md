# Codex 实时监控：更新策略与资源占用

“实时”是与“今日”“趋势”并列的独立页签。默认打开后自动更新，同时提供暂停开关与单次刷新，适合边工作边查看消耗。统计是最近 60 秒已写入日志的请求用量除以 60，包含缓存读取，不测量流式生成速度或 Agent 进程状态。

## 生图任务为何会出现对话 Token/s 为 0

实际检查发现，生图工具持续产生本地 PNG 文件时，Codex 对话请求的用量记录可以暂时没有增长。工具返回未提供真实的图像 Token；对话 `token_count` 记录不能完整覆盖生图工具内部的消耗。因此页面将“对话合计 Token/s”和“图像 Token/s”分开：前者按日志计算，后者显示“— / 未记录”，同时展示近期新图文件数、最新写入时间及目录检查时间。

图片目录每 15 秒异步检查一次，只读取文件元数据，不读取图片内容或会话提示词。重复目录不会重复计数；没有新的对话用量时，图像数据仍继续更新，刷新页面后能从文件元数据恢复。新 PNG 文件只代表本地文件写入，不能据此推算真实计费 Token、生成进度或任务是否仍在运行。

原有图片模块的“每张 20K Token 等值”是人为换算，不能用作图像实际 Token，也不进入实时 Token/s。只有来源明确提供真实图像 usage 时，才可以增加实际图像 Token/s 的统计。

| 场景 | 行为 | 判断依据 |
| --- | --- | --- |
| 打开实时页 | 默认每 2 秒更新 | 日志按请求写入，2 秒兼顾及时性和读取频率 |
| 想更及时／更省资源 | 可选择 1 秒／5 秒 | 用户可按需要调整；统计窗口仍为 60 秒 |
| 暂时不想自动更新 | 关闭开关，保留最后一次数据及更新时间 | 避免不断读取；选择会记住 |
| 关闭自动更新后想看最新值 | 点击“刷新一次” | 只请求一次，不重新开启自动更新 |
| 没有近期用量／没有日志 | 至少每 5 秒／10 秒检查 | 空闲时降低 CPU 与磁盘开销 |
| 离开实时页／浏览器在后台 | 取消待执行更新与当前请求 | 返回后按开关状态恢复 |
| 接口连续失败 | 重试间隔逐步增加，最多 30 秒 | 避免服务不可用时频繁重复请求 |

刷新周期是在上次请求完成后计算，因此不会叠加未完成的请求。各浏览器共享服务端的一次采样，避免同时重复读取。

## 内存如何控制

更新频率首先影响 CPU 和磁盘读取。内存增长更取决于是否一直累积请求明细、历史日志正文和去重记录，因此实时模块采取以下措施：

- 日志按块流式读取；第一次读取需要经过历史内容，后续只读取新增字节。
- 只保存会话身份、工作目录、模型及最近 5 分钟的数值统计，不保存提示词、回复与工具输出。
- 历史请求不进入实时去重缓存；保留最新累计基线，防止重复额度快照被当成新消耗。
- 用量及去重记录随窗口过期清理。未完成的日志行有长度上限，超大消息正文会跳过。
- 大目录发现新建／续跑会话的间隔为 15 秒；已跟踪会话的新增内容按面板频率读取。
- Windows 上文件被 Codex 持续打开时，最后修改时间可能保持不变。首次发现会检查日志末尾的实际时间，随后同时比较文件大小、修改时间与文件身份，避免把仍在增长的会话当成旧日志；不重复全量读取未变化的历史文件。
- 没有客户端请求实时数据 60 秒后释放该模块的缓存。若其他窗口仍在查看实时页，则继续共享缓存。

暂停的是实时统计请求，整个看板仍保留原有历史聚合和其他模块的功能。释放缓存也不意味着 Node 进程的总内存立即下降；运行时可能保留已分配内存用于复用。

## 可复现的模块测试

运行 `node --expose-gc tests/codex-live-benchmark.js`，程序生成并清理独立临时日志，不修改真实 Codex 会话。

2026-10-13 本机一次测试，单个日志约 30.35 MB，含 20,000 条历史请求、约 24 MB 无关消息正文和 60 条近期请求：

| 项目 | 结果 |
| --- | --- |
| 首次读取 | 约 113 ms |
| 日志未改变时的 100 次检查均值 | 约 0.18 ms／次 |
| 首次读取后新增 JavaScript 堆内存 | 约 409 KiB（0.4 MiB） |
| 保留的用量记录／去重键 | 60／60，历史 20,000 条不保留 |
| 释放后保留的文件／事件／去重键 | 0／0／0 |

这是实时模块的模拟测试，包含运行时与文件读取的新增堆开销，不是整个看板、浏览器或多会话的内存上限。实际开销随近期请求数、并行会话数、目录规模与磁盘性能变化。推荐保留默认 2 秒自动更新；仅在需要观察更细的更新时使用 1 秒。
